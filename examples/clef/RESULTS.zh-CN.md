# CLEF 自动前缀缓存的性能与一致性

在 A800 80 GB 上，每笔输入使用同一份 1500-token policy、500-token 动态业务 state 和三道题，并发 8。自动缓存把客户端拿齐三个答案的 P95 从 **956.79 ms 降至 429.79 ms**，吞吐从 **8.41 提高到 19.29 笔/秒**。三个种子的 3000 笔请求，三题的完整公开答案全部与确定性全量计算端一致。

这些时延来自迁入本 fork 前已验收的引擎及其独立环境。本文附有当时的 54 个正式窗口汇总，以下表格可从中复算。新构建的镜像、目标 GPU 或另一模型版本应另行记录实测数据。[正式窗口 CSV](formal-results.csv) · [本分支部署与验收](README.zh-CN.md)

## 业务与对照

每笔业务是一条 HTTP 请求。API state 是固定 policy 和本笔动态业务 state 的拼接，`questions` 同时含 q01、q03、q04。端到端延时从客户端发请求计到返回并解析全部三题，吞吐以成功完成的业务数除以对应窗口的墙钟秒数。完整一致指逐题逐字段比较公开 `answers`，覆盖分类结果、置信度、选项概率和连续分数。

三组分时使用同一 A800、同一模型权重、tokenizer、模板和校准，TP=1、BF16、上下文 8192、`--mem-fraction-static 0.5`。

| 组 | 条件 | 要回答的问题 |
|---|---|---|
| A，确定性全量计算 | 关闭 Radix Cache，使用确定性推理和 Triton，包含同样的联合头校准与运行适配 | 逐笔完整答案、端到端时延及引擎计算量的参照 |
| B，历史固定前缀版 | 启动时提供已知 policy 的 token 文件 | 已知边界时的性能参考 |
| C，本分支自动版 | 从普通业务请求间的 token 分叉发现可恢复边界，policy 随每笔请求传入 | 自动发现的收益及其开销 |

六组共 54,000 笔三题业务。两种优化与 A 分别有 18,000/18,000 对完整一致；A 实算 33,660,000 token，B、C 各实算 15,228,000 token。正式窗口均成功且没有重试。SP500 在单并发下只获得约 4.4 ms 的 P95 收益。主场景 SP1500、并发 8 时，自动版比预先配置边界的 B 多 13.82 ms P95，业务获得了在同一个实例内直接更换 policy 的能力。

半卡参数在所有组中相同。自动版需要保存最终隐状态，主场景下 C 的池容量为 458,498 个 token 槽、最多 60 笔在途，A 为 852,511 槽、96 笔。在共享 GPU 上，其他进程已占用的显存会影响本实例启动时的容量。原实验排除了 3 次检测到外部 GPU 计算活动的窗口尝试，随后重跑。CSV 的 `peak_device_mib` 是整张卡的采样值，`token_capacity` 和 `active_request_capacity` 是对应窗口服务的容量。

## 100 笔独立复测

2026-11-20 重新启动 A、C 两端，分别清空缓存，用相同的 10 笔输入预热。随后在 SP1500、动态业务 state 500、三题、并发 8 配置下，回放 seed 42 的同一批 100 笔输入。分词结果和题目布局逐笔对齐。

| 指标 | A，确定性全量 | C，自动前缀 |
|---|---:|---:|
| 成功业务 | 100/100 | 100/100 |
| 端到端 P50 | 944.30 ms | 388.33 ms |
| 端到端 P95 | 961.38 ms | 430.51 ms |
| 业务 QPS | 8.43 | 20.05 |
| 引擎总计算量 | 237,000 token | 83,400 token |

三题完整答案 **100/100 对一致**。C 每笔实际恢复 1536 token，P95 下降 55.22%，净计算量下降 64.81%。A、C 各执行 100 次计算尝试，两端均没有额外重试。该小样本与上面的正式窗口单独统计。

## 迁移时如何解读一致性

原生默认部署与本实验的**确定性原生对照**有数值差异。历史非确定性服务与确定性全量路径的 12,000 对可配对输入中，有 183 笔至少一题标签改变；这个差异在全量计算时已经出现。业务从历史默认配置迁移时，应分别测量切换确定性设置产生的变化，以及在同一数值设置下启用缓存产生的变化。

旧环境还测过容量压力和失效重试。受限池中的 16 笔请求取消后，曾写入的 2338 个物理槽得到复用，压力阶段 30 笔正常完成请求均与 A 一致。注入失效槽的独立测试里，一个 2373-token 输入先续算 837 token，验证失败后完整重算 2373 token，总成本 3210 token，最终答案与 A 一致。上线时可先在目标 GPU 运行三笔串行检查、核对计数和整份答案，再使用代表性业务输入测 P95 和业务 QPS。[本分支验收入口](README.zh-CN.md)
