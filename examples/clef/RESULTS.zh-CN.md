# CLEF 自动前缀缓存的性能与输出一致性

同一模型在同一张 A800 80 GB 上，六种测试配置的完整答案均与确定性全量计算一致。自动缓存的端到端 P95 降幅随输入和并发变化，从 4.85% 到 64.33%。例如，固定指令为 1500 个 token、并发为 8 时，P95 从 **956.79 ms 降至 429.79 ms**，吞吐从 **8.41 提高到 19.29 请求/秒**。

## 测试输入与对照组

测试客户端向 `POST /v1/systemone` 提交 `state` 和 `questions`。为得到可比较的负载，本次实验在 `state` 开头放一段重复使用的固定指令（fixed instructions），随后拼接每个请求独有的 500-token 文本，并在 `questions` 中放入三个问题。固定指令取 500 或 1500 个 token，并发取 1、8 或 16。长度、问题数和并发度都是客户端构造这批样本时的设置。引擎根据模板渲染和分词后实际相同的 token 开头，选择可恢复的检查点。[前缀匹配与恢复原理](DESIGN.zh-CN.md)

三组服务分时使用同一张 A800、同一份 Qwen3.5-4B CLEF 联合分类模型权重、分词器、模板和校准参数。均采用单卡（TP=1）、BF16、8192-token 上下文和 `--mem-fraction-static 0.5`。

| 组 | 计算方式 | 用途 |
|---|---|---|
| A，确定性全量计算 | 关闭 Radix Cache，使用确定性推理和 Triton | 比较同一数值设置下的输出、端到端时延与计算量 |
| B，预先指定边界 | 历史实现，启动时从文件读入已知的固定前缀 token | 测量已知边界时的稳态速度 |
| C，自动发现边界 | 同一实例从请求的共同开头发现并保存可恢复的检查点 | 测量本分支采用的自动缓存机制 |

客户端从发出 HTTP 请求开始计时，到收到并解析该请求的全部答案为止。吞吐以测量窗口内成功完成的 HTTP 请求数除以窗口秒数，单位为请求/秒。完整答案一致指返回的 `answers` 按问题、按公开字段全部相等，包括分类结果、置信度、选项概率和连续分数。

## 稳态性能

每种配置使用三个随机种子（42、43、44）。每个种子先发送 30 个预热请求，再测量 1000 个请求。每个格子依次给出 **P50（ms）/ P95（ms）/ 吞吐（请求/秒）**。各指标先在单个窗口计算，再对三个种子的窗口等权取均值。以下数据来自迁入本 fork 前已验收的引擎环境，54 个正式窗口的汇总值可用于复算。CSV 保留了发布时的列名，`policy_tokens` 记录测试输入的固定指令长度，`business_qps` 表示每秒完成的 HTTP 请求数。[逐窗口 CSV](formal-results.csv)

| 固定指令长度（token） | 并发 | A，确定性全量 | B，预先指定 | C，自动发现 | C 相对 A 的 P95 降幅 |
|---:|---:|---:|---:|---:|---:|
| 1500 | 1 | 137.33 / 141.66 / 7.25 | 79.70 / 84.70 / 12.42 | 82.42 / 88.84 / 12.00 | 37.28% |
| 1500 | 8 | 951.17 / 956.79 / 8.41 | 407.19 / 415.98 / 19.68 | 417.61 / 429.79 / 19.29 | 55.08% |
| 1500 | 16 | 1762.56 / 2113.12 / 8.53 | 724.07 / 733.83 / 21.98 | 740.99 / 753.79 / 21.53 | 64.33% |
| 500 | 1 | 87.02 / 90.62 / 11.42 | 75.48 / 80.77 / 13.12 | 81.12 / 86.22 / 12.22 | 4.85% |
| 500 | 8 | 535.57 / 540.64 / 14.92 | 365.52 / 373.79 / 21.82 | 374.94 / 396.95 / 21.08 | 26.58% |
| 500 | 16 | 957.89 / 1271.79 / 15.68 | 692.63 / 712.63 / 23.03 | 714.81 / 728.38 / 22.30 | 42.73% |

54,000 个正式请求全部成功，均无重试。B 与 A、C 与 A 分别有 **18,000/18,000** 对完整答案一致。A 实际计算 33,660,000 个 token，B 和 C 各计算 15,228,000 个。自动发现相对全量计算的绝对收益在短输入、低并发时较小。固定指令为 500 个 token、并发 1 时，P95 仅下降约 4.4 ms。固定指令为 1500 个 token、并发 8 时，自动发现的 P95 比预先指定边界高 13.82 ms，同一实例可接收不同的共享前缀。

缓存最终隐状态需要显存。在固定指令为 1500 个 token、并发 8 的窗口，C 的池容量为 458,498 个 token 槽，最多 60 个在途请求，A 为 852,511 槽、96 个在途请求。两组使用相同的显存比例。原测试排除了 3 次观测到外部 GPU 计算活动的窗口并重新测量。CSV 的 `peak_device_mib` 记录整卡显存采样值，`token_capacity` 与 `active_request_capacity` 记录对应实例的容量。

## 新前缀何时真正少算

下面三组测试都从空缓存开始。每组串行发送三个请求，保留相同的开头，每次更换后续文本。单元格依次列出 **匹配的 KV token 数 / 实际恢复的 token 数 / 本次新发布的检查点位置**。这些位置针对模板渲染后的完整模型输入，可能包含固定指令之外的模板 token。[诊断字段定义](DESIGN.zh-CN.md)

| 测试输入 | 第 1 个请求 | 第 2 个请求 | 第 3 个请求 | 第 3 个请求实际计算 / 总输入 |
|---|---:|---:|---:|---:|
| 1500-token 固定指令 | 0 / 0 / 2368 | 1542 / 0 / 1536 | 1542 / 1536 / 2368 | 834 / 2370 |
| 500-token 固定指令 | 0 / 0 / 1344 | 542 / 0 / 512 | 542 / 512 / 1344 | 858 / 1370 |
| 另生成的一段固定指令 | 0 / 0 / 1600 | 832 / 0 / 832 | 832 / 832 / 1600 | 828 / 1660 |

以第一行为例，第二个请求匹配了 1542 个公共 token，实际恢复量仍为 0，完成时发布了位置为 1536 的检查点。第三个请求使用该检查点，只计算余下 834 个 token。另有一组保持整个 `state` 相同并替换问题，第三个请求恢复了 2048 个 token。包含不同长度、不同请求顺序的检查共 51 个请求，全部与 A 的完整答案一致。

| 指标 | A，确定性全量 | C，自动发现 |
|---|---:|---:|
| 成功请求 | 100/100 | 100/100 |
| 端到端 P50 | 944.30 ms | 388.33 ms |
| 端到端 P95 | 961.38 ms | 430.51 ms |
| 吞吐（请求/秒） | 8.43 | 20.05 |

**100/100 对完整答案一致**。C 每个请求实际恢复 1536 个 token，P95 下降 55.22%，计算量下降 64.81%。两端均执行 100 次计算，无重试。

## 槽回收、重试与数值设置

原环境还测试了缓存池压力与失效槽的处理。16 个请求取消后，它们写过的 2338 个物理槽重新投入使用。压力测试中正常完成的 30 个请求均与 A 输出一致。另一组测试主动制造槽失效，一个 2373-token 的请求先计算了 837 个后缀 token，校验失败后重新计算全部 2373 个，总计算量为 3210 个 token，最终答案与 A 一致。

上文的完整一致性以确定性全量计算端为参照。在另一项历史比较中，12,000 对输入在非确定性默认设置与确定性全量设置下都有输出，其中 183 对至少有一个问题的标签不同。评估已有部署时，先比较两种数值设置下的全量结果，再在同一确定性设置下比较开关缓存的结果。
